### 1. 别用 Google Play 订阅 Claude：一篇把 Android 遥测拆成「六关」的正反手教学
[https://linux.do/t/topic/3180147](https://linux.do/t/topic/3180147)

- **核心分类**：开发调优 / 移动端遥测与账号风控（短名单 s=41.6、第 3 位，1,321 浏览 / 91 赞 / 51 回复；正文约 3,400 字，是当天最成体系的技术长文）。作者明说这是 11-14 期头条 3176715《为什么不建议头铁折腾 Claude》的续篇——「鉴于旧帖有很多佬友认为我写的很对，但是没什么用，那我来波正反手教学」，即上篇给理论、这篇给「坠机小技巧」的反面清单，落点是「不要使用 Google Play 订阅 Claude」。依据是他所称的「野生逆向报告」：Claude Android App 会记录 SIM 卡相关信息，且 Android 的 `SubscriptionManager` 是不需要用户同意就能静默读取的 API。
- **解决痛点**：社区里防封攻略多停留在改时区、换 IP、挂家宽这类单点操作，很少有人系统说明「手机端在没登录、没开代理时就已经泄露了什么」。这篇要回答的是：为什么你觉得已经伪装干净了，号还是一个接一个地寄。
- **技术要点与核心流程**：作者按「六关」逐层加码。第一关是首次启动 App（**并不需要登录**）时理论上可读的 SIM 卡信息：国家码、运营商名称（SPN）、数字编码、细粒度运营商 ID（能区分原生 T-Mobile 与 UltraMobile 这类海淘卡）、每个卡槽插卡状态、单双卡能力、eSIM 硬件支持度、默认卡的自增订阅序号（「甚至能知道这是你手机插过的第几张卡」）、当前驻留 / 附近基站国家码、连接基站运营商、国际漫游状态、开关与系统 VPN 状态——「插着一张美国卡，用美国 IP 访问 Claude，你的美国卡怎么告诉我在漫游？」。第二关是无感上报：Anthropic 相关域名并未被国内屏蔽，因此无论开不开代理、登录与否，这份数据「已经漂洋过海」。第三关是绑定真机指纹：这些数据与 `ANDROID_ID` 一起上报，不主动重置系统就不变，「一个号寄，后面号接着寄」是因为设备已成高危设备。第四关针对「拔卡 + 刷机」：按国际标准即便拔掉 SIM，基带仍会搜附近基站以保证能打紧急电话，「无信号」是骗你的，附近是中国移动基站反而成了更强的证据。第五关针对「飞行模式 + 全局代理」：逆向报告称 App 会调用 `NetworkInterface.getNetworkInterfaces()` 枚举地址、仅排除回环，于是 `192.168.1.2` 与 `2409::` 这类路由器下发的公网 IPv6 会暴露运营商与地市，「它是否真的可达，这不重要」。第六关针对模拟器：Google 签发 `MEETS_DEVICE_INTEGRITY` 真机认证，依赖手机出厂烧录在芯片里不可导出的根私钥，模拟器无法证明「这是一台真机」。作者给出的「唯一规避办法」是一串自嘲式清单（彻底重装、拔卡、飞行模式、关光猫 IPv6、软路由全局代理、用真机、跑路不用 Android / 改买无锁外版 iPhone SE3），并补一句 iOS 也有遥测、只是 Apple「没有 Google 那么傻逼，把底裤都给人家看了」；最后回到上篇的信息不对称论证：Anthropic 可以随机封号、延迟封号，所以「没被封的号」证明不了这些点不敏感，那本身就是幸存者偏差。
- **价值总结与实践建议**：先说清可信度边界——全篇因果链来自作者转述的「野生逆向报告」与 Android 开发者文档，正文没有给出该报告的链接、日志或对照实验，「Claude 实际读取并上报了哪几项」属**逆向推断而非官方确认**，六关里多处用「理论上」「好难猜啊」的表述，读者应按威胁模型读、不是按实测报告读。评论区的补充与反驳要如实记：@Stesla 提出「用 device faker 等具有 root 权限的模块，可以解决指纹问题，利用 surfing 透明代理的 tun 模式完全也可以解决 ipv6 泄露问题」，并指出「很多美版机 pixel 也是锁特定 esim 的……还有不支持老手机也是不支持的」「我 root 机也掉，再说现在 keyb…（截断）」——即第一关与第六关的具体判定在真机 / root 环境下未必如作者写得那么整齐；@Louis2、@lKUN 只是帮顶，不构成验证。对照本期第 2 篇（网络端 IP 分流）与 3179567 那批「没挂反代也被封」的一手遭遇，更稳妥的读法是把两篇合起来当一份**攻击面清单**：设备端（SIM / 基站 / IPv6 / 真机认证）与网络端（出口 IP / 定位 / 登录态）都可能成为信号，且平台侧存在离线评估与随机封号，任何单点的「我这样用一直没事」都无法证明因果。实践上最不划算的是为了对齐这些指纹持续投入（刷机、拔卡、买外版机、折腾 eSIM）；若确有稳定使用需求，优先检查支付 / KYC 一致性这类更硬的信号，并接受「防封没有可证明的解」这一结论。别把这篇或上篇任何一篇当定论，更别为了验证去碰明确违规的手段。

### 2. 从 IP 下手避开风控：一份写了额度管理、账号池与「送中」自查的 vibe coding 教程
