### 1. [通了个宵，终于把 Super-Agent 架构玩明白了](https://linux.do/t/topic/3109398)

- **核心分类**：Agent 架构 / 工程解读
- **解决痛点**：作者 cxuanAI 转述 DeepSeek Harness 团队（下称 DSH）的判断：现有 Agent 以**单个 Session** 为单位、彼此独立，人手动切换 Session 时注意力跟不上——**个人注意力只能覆盖约 3~5 个 Session**。「单任务的上限取决于模型能力，多任务的上限取决于人的注意力」，即便用 MCP 解决扩展性，仍受限于上下文混乱与单会话同步阻塞。Super-Agent 要解决的正是「一组任务如何长期并行推进、同时让人少操心」。
- **技术要点与核心流程**：作者把 DSH 的五个模块逐一拆开：① **双层架构** —— Router 常驻全局路由层，负责与人交互、汇总跨任务信息、只做分发不执行具体任务（DSH 建议用轻量模型即可）；Worker 各上下文隔离、挂完整执行工具、专注单一任务，需配最强模型，复杂任务可再 fork subagent 成为 Agent Teams。底层接管上下文管理与并发，**从用户侧淡化 Session**。② **事件驱动** —— 群聊、邮件日程、代码审查评论、CI 结果都是 Trigger，相关 Trigger 连成 Thread；降噪分两层：程序层策略 Fast Path 先滤掉噪音，语义层 Slow Path 才交给 LLM 判断；过滤后的消息**直接路由给订阅该 Thread 的 Worker**，全局 Router 只负责新任务冷启动与跨任务协调。上下文注入借鉴编译优化提出 **Inline / Spill**（近期常用信息内联进窗口，超预算或低频信息留引用摘要按需读取），并用**链式召回**给 Trigger / Thread / Worker 编 ID、注入时带上「下一跳 ID」连成引用图；另有借鉴**投机执行**的后台提前尝试。③ **多信道交互** —— 用**异步 ReAct Loop** 消除后台耗时任务对前台对话的阻塞（全双工，`start()` 立刻返回而非 `run()` 卡住等结果）；作者核对后指出 Claude Code 的后台 subagent、ChatGPT 长任务中追加约束已有类似能力，DSH 中该机制**已实现但尚未默认开启**。④ **计算、状态与环境分离** —— Agent Loop 放云端可替换容器、会话状态单独存数据库；**本地环境不搬上云**，端侧装轻量 daemon 只执行命令回传结果，即 BYOM（Bring Your Own Machine），代价是云端与端侧必须互信。⑤ **Watchdog** —— 在主系统之外设独立控制回路，因为 Agent 的故障往往不是进程死掉而是「LLM 内部循环死锁或偏离目标」，看门狗以定时消息驱动介入纠偏，本身也是一个可询问的 Agent Session。作者还对比了 Claude Code 那篇「单 Agent + Main Loop」：那篇优化的是**一项任务内部**多专家交接的信息损失，DSH 这篇组织的是**跨任务**的长期执行。
- **价值总结与实践建议**：7502 浏览/1177 赞/154 回复，@Acris「熬夜看完这篇，路由和工作者那段最明白」，@ethan08 感慨「没想到有用的信息是以这种方式流到我身边」，@BAMBOOKING 说正准备学写 DSH 插件、看到这篇有了方向。三点判断：① 最值得带走的不是名词，而是**「Session 不该成为用户负担」**这个产品判断 —— 作者直言很多 multi-agent 项目把用户当项目经理，路线不对；② Inline / Spill 与 OS 换页**形似而神不似**：缺页由内核自动处理，Spill 出去后模型得自己意识到引用存在并主动调工具读回，因此**对模型能力要求更高，换模型效果会差很多**，作者自己点破了这一点；③ 这是**作者对官方文章的消化转述**，不是一手论文，且异步 ReAct「尚未默认开启」、BYOM 有信任前提，落地时别把架构图当已发布能力。作者文末那句「终于有正经团队从底层动刀子，而不是天天玩一堆 tools 和 skills」是个人立场，读的时候心里有数即可。

### 5. [搞中转站一年了：支付、服务器、域名、CDN 经验帖](https://linux.do/t/topic/3106621)

- **核心分类**：工程实践 / 服务部署
- **解决痛点**：主帖只有短短几行，但这个「开源模板 + 支付 + 网络」的组合拳，恰好是很多人想搭中转站时最缺的那张地形图；真正的技术密度在作者自己的高赞回复里。
- **技术要点与核心流程**：作者 dualseason 给出四块：① **开源模板** —— newapi 与 sub2api 两个；② **支付** —— 走易支付协议（源项目彩虹易支付），可用插件接各种渠道，其中**码支付**的原理是个人收款码 + 一台旧手机监听收款通知做程序回调；③ **服务器** —— 国内需域名备案，香港机器若非精品回归网速很慢，一般用三网优化（CN2 一类）；④ **CDN** —— 套 Cloudflare 容易成「减速云」，作者观察到中转站普遍**至少备两个域名：一个套 CDN、一个直连不套**。回复区里 @Enetso 问「服务器和调用量之间有啥关系、要不要扛 D」，作者补充了最关键的一段：newAPI 与 sub2api 都是 **Go** 写的，协程能力没问题，**问题出在设计** —— 它们是「先承接住全部流量 → 放行 → 再落数据库计费」，天然存在**数据库并发瓶颈**；要做到企业级调用必须二次开发，把实现方式改成**旁路监听 + 异步落库**；服务器核数越大能开的线程越多、确实更能扛并发，但这个上限很低，不是正解。
- **价值总结与实践建议**：3832 浏览/348 赞/152 回复。@Qwen4 的追问代表了不少人的真实关切：「老如果能讨论一下怎么批量开号拿号、防封、防降智就好了，我觉得这才是中转站的价值」—— 但这条线作者没有展开，**帖子里没有任何关于绕过平台风控的内容**，别把提问当成答案。三点判断：① 最有复用价值的是那段**「流量路径决定瓶颈」**的分析：同步落库计费是这类网关的通用天花板，换语言没用、加核数也只是缓解；② 「套 CF 变减速云 / 双域名」是经验观察，**没有给出测速数据**，实际要不要套取决于你的用户分布，别照抄；③ 涉及支付与账号合规的部分（码支付、备案、批量注册）风险不低，本文只做技术记录，不构成任何经营建议。
