### 2. 权重不会说谎：前 OpenAI 研究员用「初始化指纹」指认六个国模用了禁售 Blackwell，以及它证明不了的部分
[https://linux.do/t/topic/3167685](https://linux.do/t/topic/3167685)

- **核心分类**：前沿快讯 / AI 取证与出口管制（短名单 s=35.5，2,546 浏览 / 147 赞 / 33 回复）。主帖只有两张截图加一句「出处见图，推特原文里面有完整报告的链接」，属典型薄帖——**以下技术细节全部来自 WebSearch 核实的公开报道与报告本身，不是主帖正文**，按写作要求先核实再落笔、不臆测参数。
- **解决痛点**：出口管制长期只能查「芯片卖去了哪」，缺少事后可验证的技术证据。这份分析把「已经公开发布、谁都能下载的模型权重」变成了取证对象；但同样容易被读成「走私实锤」，所以更该讲清「能证明什么、不能证明什么」。
- **技术要点与核心流程**：11-12，前 OpenAI 研究员 Will DePue（2023 年加入、参与 Sora 及 o3 / GPT-4o 后期训练，现以独立机构 Unemployment Labs 发布）称从公开模型权重里恢复出硬件指纹。原理是：大模型权重用带种子的伪随机数初始化，PyTorch 按 GPU 的流式多处理器（SM）数量排布随机数线程——H100（Hopper）132 SM、B200/B300（Blackwell）148 SM、GB200/GB300 152 SM，因此初始值的内存布局自带芯片代际特征；训练会覆盖大部分初始值，但每个大模型总有若干「保留行」（preserved rows）几乎未被改动，可据此反搜「种子 + 布局」组合。方法上扫描了约 **6 万亿**种组合，全搜索空间内偶然误配的上限约 8 sigma，而真实匹配最弱的单项也有 20 sigma、全模型匹配 49~1,385 sigma。实机验证最有说服力：租来 H100 与 B300 跑未修改的 PyTorch，用还原出的 DeepSeek 种子 953049583，在 H100 上逐位复现了 DeepSeek-V3 全部 57,344 个保留值、却复现不了 V4-Flash 的任何一行；在 B300 上 V4-Flash 469 行中 461 行相关系数 >0.99（445 行逐位相同），种子改动 ±1 则全部失效；租用的 GB200 用 Moonshot 种子 20256586 复现了 Kimi K3 全部 13 个保留行，AMD MI300X 亦无法复现。涉及四家实验室六个模型：DeepSeek-V4-Flash / V4-Pro、Kimi K3 / K3.1-Pro、MiniMax-M3、蚂蚁 Ling-3.1-flash，其中两个匹配 B200/B300、四个匹配 GB200/GB300；Qwen、GLM、腾讯、小米、StepFun 等仍呈 Hopper 特征，另有一个模型无英伟达指纹。方法还用 24 个开发者公开过训练硬件的模型做 ground truth，全部吻合。报告自估最大两次训练各用 2,000~3,000 张 Blackwell、四家合计受限 GPU 价值超 5 亿美元。
- **价值总结与实践建议**：站内评论区的三条质疑恰好命中报告自己声明的局限，必须如实写。@zzyx1088「难道我不能把数据中心建设到国外来训练模型吗」对应报告明说的：指纹只标识**权重初始化所用的硬件**，不必然证明全程训练都在该硬件上，更**不证明芯片的物理位置**——通过第三国数据中心、租赁算力或合规漏洞取得 Blackwell 会留下同样的签名；@fola「在这个节骨眼上的新闻是故意要引起千夫对英伟达（和黄仁勋）的责难啊」提醒发布时点与当日人事地震高度重合，动机属猜测；@Stesla「这不很正常吗？难道还能是华为卡训练的吗」则是把技术推断直接当既定事实。还要写清可信度边界：报告**未经同行评审**、出自单一小型独立机构，DePue 称 OpenAI 与 Anthropic 资深研究员已独立验证，但两家公司均未公开置评、报告未列外部审查人，英伟达亦未回应置评请求；报告自己的措辞是「支持、但不证明」Blackwell 也执行了训练，且该分析**本身不构成违反出口管制的证明**。真正可复用的技术贡献是「给定开源权重往往能反推初始化芯片族」这一取证原语——ground truth 全对、种子 ±1 即失效、方法公开到任何有物理 Blackwell 与权重文件的人都能复核，未来几周的第三方复现才是关键。政策侧值得留意的是监管对象从「芯片流向」延伸到「模型权重与算力租赁合同」这一转向，而不是据此给任何一家实验室下结论。

### 4. 宝塔面板 Fail2ban「正常运行」却一条规则没加载：两个代码级 BUG 与可复现验证
[https://linux.do/t/topic/3169321](https://linux.do/t/topic/3169321)

- **核心分类**：Develop / 运维安全 · 面板插件代码审计（短名单 s=29.0，885 浏览 / 45 赞 / 24 回复；正文 2,105 字，当天技术密度最高、唯一给出可复现代码级证据的一篇）。
- **解决痛点**：作者本想给宝塔免费防火墙配个轻量 WAF，顺手复用面板软件商店里的 Fail2ban 插件，结果发现它在 Ubuntu 24.04+ 上「面板显示正常运行、实际一条规则都没加载」——安全产品给的是情绪价值，不是防护。
- **技术要点与核心流程**：分析基于宝塔面板 Fail2ban 2.6 代码。① **日志路径过时且强制载入**：内置 sshd 规则仍指向 `/var/log/auth.log`、ftpd 指向 `/var/log/syslog`，而 Ubuntu 24.04 起默认移除 rsyslog、SSH 登录日志全进 systemd-journald，两个路径默认都不存在；sshd / ftpd 规则又被强制载入（用户不装 ftp 也加载）。Fail2ban 只要发现任一已启用规则的日志文件不存在，就会**拒绝重载整个配置**，于是面板上「正常运行」的 Fail2ban 实为空转。② **BUG 1：重载永远提示成功**（`fail2ban_main.py` 138 行）：`a, e = public.ExecShell("fail2ban-client reload")` 后判断 `if "ERROR" not in a:`，但报错信息全部输出在 stderr（e）、stdout（a）为空，判断条件恒真；更离谱的是 else 分支 `public.returnMsg(True, "重载失败 {}".format(e))` 把状态硬编码成 `True`。③ **BUG 2：只看进程不看规则**：`if os.path.exists(sock): return True`——只要 fail2ban-server 进程没崩、sock 文件在就返回「运行中」，一条规则没加载也算正常。④ **左右脑互搏**：`_check_main_conf()` 初始化 jail.local 时认定 `[ftpd]` 的 `logpath = /var/log/syslog`，到 `set_ftpd_anti()` 里又写 `self._check_log_exist('/var/log/messages')`。作者给了可复现命令：`sudo fail2ban-client reload`，若返回 `ERROR ... Have not found any log file for 'sshd' jail` 或 `'ftpd' jail` 即中招；并关联其前一篇对免费防火墙 8.5→8.6 的审计（自述「30 多个问题只修改 5 个、修好 1 个、4 个修一半」）。
- **价值总结与实践建议**：评论区几乎一边倒玩梗（@weimutter8「这个世界就是草台，何况它还叫 BT」、@626 提醒官方号还在），但楼主补的一条更重，必须如实记：@cnmoon「一直装死中，对于免费防火墙，一直偷偷静默上传用户文件的事情，一直没回复，只是光速改了代码，在前端移除的功能（但后端代码还留着）」——这是比 Fail2ban 空转严重得多的指控，但属楼主单方陈述，未见官方回应或第三方复现，本内参不把它当已确认事实。同样要标注局限：全部分析基于 Fail2ban 2.6 单版本代码、单台环境，未验证新版是否已修，Ubuntu 24.04 的日志路径结论也需在自己环境复核。实践建议很具体：**别用面板上的「运行中 / 重载成功」判断防爆破是否生效**，直接 SSH 里跑 `sudo fail2ban-client reload` 看是否报 `Have not found any log file`，再用 `fail2ban-client status <jail>` 确认规则真的加载；Ubuntu 24.04+ 把 sshd 日志源切到 systemd-journald（`backend = systemd`）或恢复 rsyslog，禁用用不到的 ftpd jail，避免「一个缺失日志拖垮全部规则」；生产环境不要把免费面板的 WAF / Fail2ban 当唯一防线，至少用独立日志与告警交叉验证，并关注官方是否回应静默上传的指控。
