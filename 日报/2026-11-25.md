  `AND,((DOMAIN,play.googleapis.com),(PROCESS-NAME,language_server.exe)),REJECT`
  `AND,((DOMAIN,play.googleapis.com),(PROCESS-NAME,agy.exe)),REJECT`

- **价值总结与实践建议**：社区反馈要如实写：@laihaha 的「关了也会上传」与作者确认是最有价值的一条，@Sinohunk 的「我一直挂着没遇到」则提示别把个案当普遍故障。实践上：① 代理流量异常先看**按域名 / 按进程的 30 天统计**，比凭感觉猜「最近是不是下多了」有效得多；② 用 `DOMAIN + PROCESS-NAME` 的 AND 规则精确拦截，避免全局 REJECT 误伤其他服务；③ 「在设置里关掉遥测」不等于「进程不再上传」，涉及计量 / 额度的工具要用抓包或流量统计复核；④ 这类插件并发 RPC 会同时吃流量与额度，长期挂着的 IDE 插件应定期审计；⑤ 结论按作者自述与评论区复现情况参考，未控制变量、不同平台表现可能不同；⑥ 与 11-24 期 t3code 遥测争议、本期 3238873 的当事方时间线合看，第三方 harness / 插件会接触源码、账号与工作区，装前先看数据流与权限声明，别只看 UI 截图。

### 5. Agent Memory 的「熟悉又陌生」：把认知科学四分类与上下文工程放回同一张图
[https://linux.do/t/topic/3236449](https://linux.do/t/topic/3236449)

- **核心分类**：文档共建 / AI Agent 技术科普（主帖 3236449：591 浏览 / 102 赞 / 21 回复，作者 Pinkman1893，清洗后主帖 8,110 字，已补读被截断的后半段；标题标注「（上）」，作者说明分两篇）。本节只引用主帖实际写出的概念、时间线与参考资料，不对外部产品作背书。
- **解决痛点**：日常用 Agent 时接触的是上下文窗口、上下文压缩；读教材时被塞进「四种记忆类型」；看技术文章时又冒出 RAG、外部数据库、Mem0。三套词汇互相重叠，让人觉得 Agent Memory「熟悉又陌生」。作者把混乱的来源指出来：其实是**认知科学视角**（记忆承担什么认知功能）与**工程实践视角**（在有限窗口下如何实现）两条线被混着讲。
- **技术要点与核心流程**：① **双源起源**——Memory 的理论体系并非诞生于 LLM 领域：2023-04 斯坦福《Generative Agents》提出记忆流（只追加的时间戳日志 + 检索 + 定期归纳），是首个代表性完整 Agent 记忆架构；2023-09 CoALA 借鉴认知心理学与 Soar 等传统认知架构，把工作 / 情景 / 语义 / 程序性记忆系统化纳入语言智能体；工程线则是 LangChain 2022 年就把 memory 做成可插拔模块、MemGPT 借鉴操作系统分层内存管理在层级间搬数据以突破窗口限制。作者总结：认知科学路线更接近人类心理架构类比，工程路线的隐喻更接近操作系统「给外部存储换页的调度器」。② **先排除易混概念**——参数记忆（基模权重）属预训练 / 后训练范畴、不在记忆系统讨论范围；外部知识库经 RAG 引入，既可与 Agent Memory 并列交叉也可只作其组件；Context 是模型单次推理能看到的全部 token（含系统提示、对话历史、检索结果、工具返回）。③ **四类记忆（按功能分类，不是四个数据库）**——工作记忆 / 短期记忆（当前任务活动状态，对应当前 Context；受窗口限制需要摘要取舍，即上下文压缩）、情景记忆（带时间、行为、结果的具体经历）、语义记忆（提炼出的事实与规律，如「数据库连接池耗尽可能导致登录请求失败」）、程序性记忆（如何执行任务，skills / 工作流 / 系统提示词 / 工具列表乃至 harness 程序都属此类）；作者用「登录失败 Bug」的例子区分情景与语义：问「是否曾发生过」检索情景，问「为什么」检索语义。④ **典型运行流程**——接受请求 → 推理前从长期记忆检索加载 → 注入上下文 → LLM 推理决策执行 → 按需更新 / 遗忘 / 写回长期记忆。⑤ **记忆与 Context 的关系**——记忆类型是「承担什么认知功能」，Context 是「当前实际提供了哪些信息」，二者不互斥也不并列；作者引 A/ 的释义把 Context Engineering 概括为「让合适的信息在合适时机进入上下文」，并用六条示例（临时要求、带日期的回滚经历、项目经验、退款流程、用户偏好、回答前先说结论）让读者自测归类，强调归类不绝对互斥。⑥ **上下文工程三策略**——上下文缩减（裁剪重复 JSON / 三轮前工具返回、总结摘要；简单有效但信息不可逆受损）、上下文卸载（把原始内容移到外部存储并保留最小标识引用，便于找回）、上下文隔离（多智能体系统中主 Agent 只下发任务收结果，子 Agent 只返回结果，避免主干上下文被污染）；LangChain 归纳为 Write / Select / Compress / Isolate。⑦ **边界**——作者明确「四类记忆是经典认知功能分类、不是唯一理论体系」（另荐综述《Memory in the Age of AI Agents》），本篇只铺理论基础、工业实践路线留到下篇，并自承「组织内容写了快两天」「有些方面还是不太成熟，恳请指正」；文末列 CoALA、Generative Agents、MemGPT、Lilian Weng、LangChain Context Engineering、Anthropic《Effective Context Engineering for AI Agents》、Manus 上下文工程实践等参考资料。
- **价值总结与实践建议**：评论区认可度高且问到了点子上：@neo「来学AI了。字多给精华」、@Srpihot「memory 目前有大一统的算法吗」、作者 @Pinkman1893「始皇老大！我捉，这就赶下篇」。实践上：① 讨论记忆前先声明视角（认知功能 vs 工程实现），多数争论其实是在两套 vocabulary 里各说各话；② 四类记忆是功能分类，工程上不必建四个独立库，可共享存储、互相重叠，别照着分类硬拆表；③ 「情景 → 语义」的归纳、「参数记忆不归记忆系统管」这两条能直接减少设计时的范围蔓延；④ 压缩会不可逆丢信息，长任务优先用**卸载 + 最小引用**保住原始内容，这与 11-24 期精选里「长任务必须阶段性落盘、一次上下文压缩能把大半天工作归零」的实测结论互为印证；⑤ 多 Agent 架构用上下文隔离保护主干注意力，比让两个概率模型互相审查更省 token；⑥ @Srpihot 的「大一统算法」问题文中并未给出答案，作者明说工业实践放下篇，本篇按理论梳理读、别当实现方案；⑦ 文中论文、产品名与分类均为作者转述，引用前自行查证原文。
