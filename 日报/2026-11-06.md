### 3. [部分linux系统(musl)尽快升级OpenSSH，存在任意密码登陆漏洞](https://linux.do/t/topic/3128996)

- **核心分类**：前沿快讯 / 运维安全（认证绕过）
- **解决痛点**：主帖很短，只说「在基于 musl 的 Linux 系统（包括 Alpine、OpenWrt、Buildroot、Yocto，以及你所拉取的许多 Docker 镜像）中，OpenSSH 自 2016 年起就存在一个问题：本不应接受密码的账户（root、仅限密钥登录的部署用户、LDAP 用户、Alpine 在 AWS/Azure 镜像中的默认用户），竟然会接受任何长度超过 256 个字符的密码」，附 sshhole.com 与 OpenSSH 10.6p2 release notes 两个信源。这类「一句话警报」必须回官方公告核实触发条件与修复版本再落笔。
- **技术要点与核心流程**：核实 OpenSSH 10.6p2（2026-11-05）发布说明、NVD/CVE 记录与多家安全公告：漏洞编号 **CVE-2026-123158**（代号 *sshole / sshhole），CVSS 3.1 **8.1（高危）**，CWE-394（意外的状态码或返回值），由 Wakefield 研究员 Özgün Kültekin 报告。成因是四项各自合理的历史设计叠加：/etc/shadow 密码字段为单个 `*` 表示禁止口令登录；musl 的 `crypt()` 失败（口令超过 256 字节上限）时返回一个不可能匹配的字符串，musl 选的正是 `*`；OpenSSH 2016 年修 CVE-2016-6210 时，为拉平用户名枚举的时间差，会对没有合法哈希的账户借用其他账户的盐做一次完整哈希；于是超长口令 → crypt() 返回 `*` → 与 shadow 里的 `*` 比对相等 → 认证通过。**触发需同时满足**：musl libc、sshd 未启用 PAM、PasswordAuthentication yes、存在密码字段为 `*` 的账户、且机器上另有一个 `$5$`/`$6$` 哈希账户供借盐；口令长度 257–1024 字节。**不受影响**：glibc 主流发行版（Ubuntu/Debian/RHEL/Fedora/SUSE/Arch 等）、启用 PAM 的构建、OpenBSD、Dropbear、密码字段为 `!`/`!!` 的锁定账户、已升 10.6p2。Alpine 已把修复回移植到 3.16–3.24 各分支（版本号不升，**`sshd -V` 看不出是否已修**，要按分支对照公告）。修复：升级到 10.6p2 或发行版修复包后**必须重启 sshd**（升级包不会替换正在运行的守护进程）；临时缓解设 `PasswordAuthentication no` 并保留带外通道。检测：从 shadow 反查 `Accepted password for <*账户>`，`*` 账户出现口令登录成功即为强异常，应视同已失陷。
- **价值总结与实践建议**：840 浏览 / 37 赞 / 18 回复，热度很低但对运维是当天最该看的一条。回复里 @Rosmonti「自从AI出来了以后以前的奇葩漏洞被发现的越来越多了。。世界就是个草台班子」、@hank9999「轰轰烈烈的大更新又要开始了」、@koast18「真的嘛 感觉有点无语了 被气笑了的感觉…」。三点如实说：① 主帖标题写「部分linux系统(musl)」是准确的，**不是所有 Linux**——glibc 或开了 PAM 的机器不用连夜应急，先按上面五项条件自查再决定动不动；② 这是认证绕过、不是 RCE，但 Alpine 官方 tiny-cloud 镜像（3.18.11–3.24.3）默认 `alpine` 用户密码字段为 `*` 且有免密 doas，命中条件等效直接拿 root；③ **升级包 ≠ 已修复**，一定重启 sshd，并用 `sshd -T` 确认 passwordauthentication、用 `apk list -I 'openssh*'` 对照分支修复版本；日志里没有异常 `Accepted password` 也不能证明没被利用（日志可被清除）。本文引用的 CVE 号、CVSS、触发条件、修复版本与排查思路均已外部核实。

### 4. [【开源】Magpie网络搜索插件，接了19家提供商，4 家免 Key 开箱即用](https://linux.do/t/topic/3132439)

- **核心分类**：Develop / 开源工具（搜索插件）
- **解决痛点**：作者常用 Magpie，觉得自带联网搜索「不多而且更新不频繁」，而各家搜索提供商送的额度放着也是过期「不用白不用」；正好 Magpie 开放了 search 钩子，于是写了 `magpie-websearch` 把官方没接入的接口接进来，目前已被 Magpie 社区收录。
- **技术要点与核心流程**：给 Magpie 的「设置 › 模型 › 网页搜索」扩充 **19 个搜索源**。免配置 API Key、匿名调用的 4 家：AnySearch、Keenable、Parallel、TinyFish；需自填 Key 的：智谱（国内 Zhipu / 国际 Z.ai）、月之暗面（Moonshot CN / Moonshot）、阶跃星辰（StepFun 独立搜索端点）、秘塔搜索（Metaso）、博查（Bocha）、Perplexity、Jina、Kagi、Linkup、Querit、Ollama、SerpApi、Serper。安装三种方式：`magpie plugin add @guotree/magpie-websearch`（npm，推荐）、`magpie plugin add github:guotree/magpie-websearch`、或在「插件 › 发现 › 给Agent的工具」里点安装；装完在设置里看到新增项，免 Key 的留空点添加、需 Key 的填入自己的。命令行等价写法 `magpie search add magpie-websearch:anysearch` / `magpie search add magpie-websearch:zhipu 你的KEY`。仓库 `guotree/magpie-websearch`，MIT 协议，作者自述「才迭代几个版本」，欢迎提 Issue / PR 加 provider。
- **价值总结与实践建议**：768 浏览 / 50 赞 / 17 回复，绝对热度不高但是当天最完整的开源工具帖。回复里最有价值的是一条**没被解答的追问**：@Preteen7645 详细描述了自己用 Magpie 反代 WorkBuddy 模型、DSH 里只配了 `workbuddy/deepseek-v4.1-flash` 且没配 MCP，却能看到联网搜索结果，贴出配置问「这个搜索结果是走的哪一个途径？DeepSeek 官方？腾讯？还是其他的第三方？」；@7up121 猜「我感觉是要把magpie的MCP配置给dsh才会走magpie的搜索吧」，楼主没有回应。三点如实说：① 这恰恰说明**插件接入 ≠ 调用链透明**——装了 19 个源之后，排查「这次搜索到底走了哪家」更麻烦，生产环境建议在网关侧记日志或固定单一 provider；② 4 家「免 Key 匿名调用」是把额度与匿名性交给第三方，别把敏感查询往上丢，也别指望稳定性，作者自己说才迭代几个版本；③ 想用的先只装 1–2 个源做对照，确认结果质量与延迟，再决定要不要为某个 Key 付费；MIT 协议 + 已被社区收录，二次接 provider 的成本很低。
