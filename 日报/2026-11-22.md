### 4. 单台 M5 Ultra 512GB 跑 1M 上下文：decode 不衰减、prefill 掉到 45%、冷启动 9.2 分钟
[https://linux.do/t/topic/3222349](https://linux.do/t/topic/3222349)

- **核心分类**：开发调优 / 本地大模型推理性能实测（382 浏览 / 24 赞 / 14 回复，2026-11-22 实测长文，作者 BlackNoise，表格数据来自服务端日志 + 客户端计时）。
- **解决痛点**：本地部署长上下文模型时，最容易被「支持 1M 上下文」一句话带过的是三件真正影响可用性的事：长上下文下 decode 会不会崩、prefill 首 token 要等多久、多并发时内存够不够。这帖用一台 M5 Ultra 512GB 把 512 → 1M 的阶梯、并发路数与 SSD 前缀缓存逐项跑出来，正好把「能跑」和「能用」分开。
- **技术要点与核心流程**：① **测试环境**——DeepSeek-V4.1-Flash-1017-MLX-Serve-Lossless，MLX-SERVE 26.11.3（MLX 0.32.5），1× Mac Studio M5 Ultra 512GB（Mac17,15）、macOS 27.2.1；服务参数 `--dspark --pld --pld-draft-len 5 --mtp-max-depth 5 --no-w8a8 --timeout 1800 --prefix-cache-mem 40GB --prefix-cache-disk off`，默认 `--max-concurrent 1`、`kv_quant off`、`prefill_chunk 8192`，`iogpu.wired_limit_mb=0`、mlx-serve 设 491,520MB；greedy（temperature 0）、关思考、`max_tokens 512`；提示用 Zig 编译器源码按路径排序拼接，靠服务端 `/tokenize` 二分裁剪精确命中目标 token 数（36 次请求全部命中）。② **阶梯结论**——1M 行提示为 1,048,576 − 512 = 1,048,064 token（给最多 512 个生成 token 留位）；**decode 中位数几乎不随上下文变慢**，512 到 1M 都在 64–74 tok/s（1M 为 65.2，256K 为 64.0）；**prefill 在 32K 达峰 4,208 tok/s 后逐步下降**，256K 为 3,475、512K 为 2,755、1M 为 1,890（仅峰值 45%）；**1M 冷启动首 token 约 9.2 分钟**（553.8 / 555.9 秒），比《M5U单机运行DeepSeek-V4.1-Flash最佳方案》外推的 5.5–7.5 分钟更长，512K 为 3.2 分钟。③ **内存**——全程最高 327.8 GB、权重本身 309.4 GB、无 swap；服务端日志 1M 会话状态 3,947 MB、512K 为 1,620 MB。④ **与 r/LocalLLM 帖对比（512~256K）**——prefill 2K 及以上快 5–19%，512 / 1K 慢 3–10%（对比帖用 26.11.2、本机 26.11.3）；作者明说生成速度不能直接比（对比帖未给提示内容，DSpark / PLD 草拟命中率取决于输出内容）。⑤ **并发**——1 / 4 / 8 / 16 / 32 路分别 62.7 / 26.3 / 14.4 / 7.7 / 3.8 tok/s，32 路峰值 506.5 GB（上限 98%）开始用 swap（仅 0.94 MB），推翻了「每会话约 3.9 GB 可放 35–45 路」的乐观估计；结论是交互不超过 4 路、批处理用 8 路（合计吞吐最高），16 路无更多收益、32 路吞吐更低。⑥ **SSD 前缀缓存**（`--prefix-cache-disk 80GB`）——1M 冷启动 557.7 秒 / 内存缓存命中 1.05 秒 / 重启后从 SSD 恢复 1.02 秒；一个 1M 条目约 3.2 GB、80 GB 约放 24 个；后台写入有约 1 分钟延迟，退出应用时未写盘条目一起写入（一次 12 个 / 32 GB / 2.8 秒），若内存缓存条目在后台写完前被淘汰则写盘取消（日志 `module export cancelled`）。⑦ **SSD 命中条件最反直觉**——会话状态含滑动窗口、只能在存盘位置原样恢复、不能截短：两份 8K 文档在重启前后各测一次，「同一文档、同一轮换问题」缓存命中 0（全部重算），「新一轮保留完整原提示」命中 8,340 / 8,357，而内存缓存里「同一文档换个问题」也能命中（8,330 / 8,341）；因此长期复用一份 1M 文档要先单独发一次只放文档（`max_tokens=1`、冷 prefill 约 9.3 分钟），之后每个问题作为第二轮 `[user: 文档原文（逐字节相同）, assistant: 任意内容, user: 问题]`，且 system prompt、日期、随机串、工具列表（条目记 `has_tools`）、思考开关与 chat 模板都必须一致，缓存目录名还与模型及加载设置绑定。
- **价值总结与实践建议**：社区吐槽集中在可读性，如实写：@yrjjun「感谢大佬的测试，但是这个这个格式有点雷霆了，实在看不懂」、@ranran「保持关注，但是正文格式确实有点懵」，作者 @BlackNoise 回应「莫急，正在调整格式中，竟然不支持原生markdown?」——**表格在论坛里被拍平后确实难读，想复现请对照服务端日志与原始表格，别照着帖内排版抄数**。实践上：① 「1M 上下文」在交互场景的真实门槛是 9.2 分钟冷启动，先判断自己是要长文档一次性批处理还是要实时问答，前者才划算；② 上 SSD 前缀缓存前先按第 ⑦ 条设计请求写法，否则「重启后命中」根本不会发生，等于白开；③ 并发别按「会话状态大小」估算路数，实测 32 路已贴内存上限，交互 ≤4 路 / 批处理 8 路更稳；④ decode 不随上下文衰减是好消息，但 prefill 掉到峰值 45% 意味着超长文档重算成本高，尽量把文档做成可复用前缀；⑤ 作者自述 256K 与 11-20 那次首轮 2,996 tok/s 的差别「可能和那次的差别有关，没有验证」，别把单轮数字当稳定基线；⑥ 这类单机实测与厂商宣传口径、他人环境数据分属不同条件，引用时保留版本号（26.11.3 / MLX 0.32.5）与提示内容，否则数字不可比。
