### 4. [防止你的 Agent 改坏刻意设计：分享一种 UX as Spec 的 Vibe Coding 工作流](https://linux.do/t/topic/3138911)

- **核心分类**：Develop / AI 辅助开发方法论（Spec-Driven 的轻量化替代）
- **解决痛点**：Agent 改一个功能时把另一个刻意设计改坏。作者举了具体例子：项目里若模型不返回 Reasoning 字段，则不显示工具调用间的思考时间、把 Tool 外显放到最外层（模式 A，类似 Codex）；若返回 Reasoning 字段，则按旧版 ChatGPT Web 的方式，以「Reasoning 块 - Tool Call 块」混排 Timeline 呈现在二级抽屉（模式 B）。Agent 搞不清要改 A 还是 B，常把仅对 B 生效的改动同步到 A，甚至删掉其中一个模式统一成另一种；有时没测到就 push 上去，长期下来项目非常混乱。作者的吐槽是「我现在都快和 GPT 一样有防御性了，写 prompt 不得不交代一堆边界」。
- **技术要点与核心流程**：先排除两条现成路——**Spec-Driven Development**（Trellis / Kiro 一类）太重，每次改动都要走 Spec → Plan → Implementation，文档开销拖慢迭代，「对于越先进的模型，往往是约束越少的环境越能发挥出其全部的性能」，防御性高的模型还会过度验收；**Memory** 也不行，作者实测 SOTA 模型仍不能很好判断哪些信息该进 Memory，通常只记用户偏好、不涉及具体功能与设计。于是提出 **UX as Spec**：维护一份自然语言的「黑盒」规范，只描述**从用户侧看到的行为（UX）**，不写代码、不写文件路径、不用高度技术化语言；有修改意图时直接改 Spec 里的描述，让 Agent 看 Diff——上下文自然带出相邻功能，Diff 同时表达现状与预期。作者对 Spec 存在意义的定义很关键：「Spec 在本质上是将功能逻辑上紧密连结、代码实现上散落各处的组分重新集合起来」，从而迫使 Agent 执行局部修改时看到与之关联的其他组分。落地约束：**尽量避免把 Spec 文件分得过细，一定按逻辑功能分**，中小型项目甚至建议单文件 Spec；作者的做法是在目录下建 `spec` 文件夹，按界面 / 大功能点分 .md（如 Settings 页一个 md、Phone Use 一个大功能），文件间联系用行内链接。他在回复里补了 prompt 模板：可用 Subagents 分区，但**按用户侧功能而非代码文件划分**，避免过多子代理与过小文件，子代理模型用 gpt-6.1-terra Medium，启动时要预判「该代理没有你的 context 可能会对任务有什么误解」并给初始指引（模板末尾被截断，未读到完整内容）。作者自己定性：「UX as Spec 是由于现阶段模型能力不足而不得不采取的临时折中方案」，Trellis、grill-me 这类工具随模型进步影响在弱化，这套方案将来也会被淘汰。
- **价值总结与实践建议**：434 浏览 / 36 赞 / 18 回复，是今天热度最低但方法密度最高的一帖。社区反馈值得原样记下：@apparition「gpt 总是把文档改的七零八落 / 只好常驻一个 grokbot 修复文档 / 会赢吗」；@Coldmood 认可「把散落各处的界面逻辑收成一份黑盒，改功能时 Agent 被迫看到相邻部分，比 Trellis 那种走完整流程轻得多」，但追问「Spec 是 Agent 从代码里抽出来的话，后面实现完会让它回写吗？要是抽的时候就漏了某个边界，Diff 里可能也看不出来」——**作者只回了一句「如有需要可以根据实际情况改动～」并贴出模板，没有正面回答回写与漏抽边界的问题**。三条建议：① 这正是该方案最大的开放缺口，照搬时应把「实现完回写 Spec」写进工作流，并人工抽查一次抽取是否覆盖关键边界；② 别把「单文件 Spec」照搬到大项目，作者明说按逻辑功能分、文件间行内链接，分太细反而丢失关联；③ 作者已声明这是临时折中，别当成长期架构投资，模型能主动检索逻辑关联的分散代码时这套就该退场。
