### 1. PHP session 反序列化 RCE：CVSS 9.2 的 CVE-2026-115560，以及「打了 10 月补丁为什么还要再打」
[https://linux.do/t/topic/3206218](https://linux.do/t/topic/3206218)

- **核心分类**：Develop / Web 安全 · 漏洞披露与升级（949 浏览 / 142 赞 / 22 回复，短名单第 1，作者 Crain）。主帖为线索式转述：给出站内前情帖 3062268、称「有了最新的进展官方评分 9.2 已经更新了补丁，大家看看有没有需要升级，已经把我加到致谢名单里面了」，并附 GitHub advisory《Session serializer mismatch can lead to remote code execution》摘要开头。⚠️ 主帖没有给出 CVE 编号与修复版本号，本节参数全部以 WebSearch 交叉核实的 php.net 官网信息公告、mallory.ai、IONIX、The Hacker News 转述为准，站内「进致谢名单」只作作者自述记录。
- **解决痛点**：PHP 站点运维最怕的不是「有个漏洞」，而是「上个月刚按公告紧急升级过，怎么这个月又来一个 9.2」。10-21 PHP 官方已为 CVE-2026-109618（OOM 内存破坏）/ CVE-2026-109619（stale global state）两个未授权 RCE 发过修复版（8.5.12 / 8.4.27 / 8.3.36 / 8.2.35），但 11-19 前后这批围绕 `session.upload_progress` 的 9.2 分漏洞是**另一条独立攻击路径**，10 月补丁并不覆盖它；大量「打完就以为结束」的站点仍暴露。这篇帖子把「有新补丁、去升级」这个动作重新推到台前，正好回答运维该问的「我到底算不算修好了」。
- **技术要点与核心流程**：① **成因**——`session.upload_progress` 开启时，multipart 上传会把攻击者可控的数据以 `php_binary` / `php_serialize` 格式写进 session 键；若同一 session 随后被以 `php` 序列化器读取，`php` 格式的 `|` 键/值分隔符会把键内字节送进 PHP 的反序列化机制（CWE-502 不可信数据反序列化），配合应用里合适的 gadget chain 即可远程代码执行，也可导致 session 损坏或拒绝服务。② **触发条件不算常见但确实存在**——应用需把 `session.serialize_handler` 设为 `php_binary` / `php_serialize`、再在 `session_start()` 前用 `ini_set()` 运行时切回 `php`；或不同应用 / PHP-FPM 池共用同一 session 存储却用了不同序列化器（此时无需运行时切换）。php.net 官网明确称这一组合「unlikely in practice」。③ **版本与修复**——CVSS v4.0 **9.2（Critical）**，向量 `AV:N/AC:H/AT:P/PR:N/UI:N/VC:H/VI:H/VA:H`；受影响为 8.2 < 8.2.36、8.3 < 8.3.37、8.4 < 8.4.28、8.5 < 8.5.13，升级到 8.2.36 / 8.3.37 / 8.4.28 / 8.5.13（或 8.6.0）即修复，修复版默认关闭 upload progress 并拒绝运行时改 `session.serialize_handler`。④ **临时缓解**——在请求解析之前（`php.ini` / FPM pool / 服务器配置，不能靠 `ini_set()` 或 `.user.ini`）设 `session.upload_progress.enabled=0` 并重启所有 worker；确保所有读写共享 session 的应用使用**同一个** serializer，或把需要不同序列化器的应用隔离到不同存储；改格式后要让旧 session 记录过期 / 迁移。php.net 11-19 的信息公告正是建议先设此项、并说明完整公告将随下个常规 bugfix 版本发布。⑤ ⚠️ **编号口径有出入，别替官方拍板**——php.net 官网把 11-19 信息公告里预告的完整 advisory 记为 **CVE-2026-115560**（并指向 10-21 的 GHSA-6wmf-4rv5-p3rp / CVE-2026-109619 里已列出的缓解项），mallory.ai / IONIX 也以 CVE-2026-115560（GHSA-658j-r8rw-q6mx，11-19 发布）描述「session serializer mismatch RCE」；但 Swiss Security Insights / Shield53 对同一批 11-19 修复使用了 **CVE-2026-126714「phpAfterShell」**（发现者 Depthfirst、同样 9.2、同样修复版本），描述侧重「session 文件写入时序 + gadget chain」。本内参只如实转述这两个编号与各自出处、都标 CVSS 9.2 与同一组修复版本，**不臆断站内帖对应哪一个编号**；站内主帖与 GitHub advisory 标题只说「serializer mismatch」。
- **价值总结与实践建议**：社区反应要如实写：@neo「搞PHP的一定要赞一下了，感谢佬友对PHP的贡献！」、@fengna「这也行吗佬友」、@dongmenleishao「这有你什么事？硬凑」——对「进致谢名单」既有认可也有质疑，作者自述不等于官方对贡献范围的完整确认，本内参只记录、不评判。实践上：① **别用「10 月打过补丁」当免检**，立刻 `php -v` 并核对 Web SAPI（php-fpm / mod_php，而不只是 CLI）的实际版本，升到 8.2.36 / 8.3.37 / 8.4.28 / 8.5.13 或更高；容器镜像要重建重部署，别只改运行中的配置。② 补丁窗口期先全局设 `session.upload_progress.enabled=0` 并重启 worker，这条配置必须落在请求解析之前；顺带审计 PHP / FPM pool / vhost / 应用覆盖 / 命令行各处的有效 `session.serialize_handler` 是否一致。③ 复用同一 session 存储的多个应用 / 池，要么统一 serializer、要么隔离存储，修完补丁这一步仍要做（官方修复不强制跨应用序列化器一致）。④ 排查 `$_SESSION` 里有无攻击者可控值；考虑迁到 Redis / DB session 存储以消除「文件型 session handler」这一类问题，但替代存储要各自复核截断行为。⑤ PHP 7.4 / 8.0 / 8.1 已 EOL、无官方修复，只有部分发行版 backport，长期方案是迁到受支持分支。⑥ 公开 exploit 已出现（漏洞库记录多个 PoC），但披露时**无在野利用报告**——「暂无在野利用」是给 defenders 的窗口，不是降低优先级的理由。
